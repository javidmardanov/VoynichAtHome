# Distribution Options for a Volunteer-Compute Platform (August 2026)

*Web-research report compiled 2026-08-30 for the Voynich@Home proposal. Every load-bearing claim carries its source URL.*

> **Correction (draft 2 of the merged design).** The conclusion drawn from the ODLK2025 case in this review was too strong. BOINC's official project guidance says projects are vetted and that attracting volunteers is a major obstacle; ODLK2025 is one documented refusal that cited maturity and perceived overlap. The supported statement is "listing is uncertain for a new small project", not "BOINC denies listings to new small projects", and no measured figure supports "installer friction cuts reach by an order of magnitude".

## 1. BOINC today: what running a project actually costs

**Server stack and requirements.** The official [Create a BOINC server (cookbook)](https://github.com/BOINC/boinc/wiki/Create-a-BOINC-server-(cookbook)) targets Ubuntu 22.04 with MySQL/MariaDB, Apache 2 + PHP, and a from-source server build; minimum VM spec 4 GB RAM / 1 CPU / 25 GB disk for dev. [ServerIntro](https://github.com/BOINC/boinc/wiki/ServerIntro) recommends production hardware of 64-bit CPU, at least 8 GB RAM, 40 GB free disk, a static IP, and ideally UPS/RAID. You operate a fleet of daemons (scheduler, feeder, transitioner, validator, assimilator, file upload handler, file deleter), cron maintenance every 5 minutes, MySQL backups (traditionally with project downtime), and permissions gymnastics between `www-data` and `boincadm`. Realistic translation for a solo dev: a $10–20/mo VPS minimum, a weekend to get "hello world" running if everything goes right, and then a long tail of Linux/MySQL/PHP sysadmin forever.

**Per-platform app packaging + signing.** You must compile and maintain separate app versions for Windows, macOS, and Linux (x86-64 and increasingly ARM), and cryptographically sign every app file with the project's code-signing key (BOINC's own key scheme, ideally on an offline machine). This — not the server — is usually the biggest ongoing tax. The newer escape hatch is BUDA (BOINC Universal Docker App), which wraps apps in Docker, but that narrows the volunteer pool to hosts with Docker/WSL.

**Do new small projects get volunteers?** BOINC's aggregate stats ([StatsXml](https://github.com/BOINC/boinc/wiki/StatsXml)) report roughly **317k active participants / 566k active hosts** platform-wide — real compute, but heavily concentrated in established projects (Einstein@Home ~16k active users; LHC@home only ~1,260 active users as of late 2024, per [Wikipedia](https://en.wikipedia.org/wiki/LHC@home)). The telling 2025 data point: a new project, ODLK2025, asked to be added to the official [BOINC projects list](https://github.com/BOINC/boinc/wiki/BOINC-projects) and was **denied, with the advice to run their app under an existing project instead** ([forum thread](https://boinc.berkeley.edu/forum_thread.php?id=15423)). BOINC's own docs acknowledge that attracting volunteers is the main obstacle to new projects and push the "coordinated model": [Science United](https://github.com/davidpanderson/science_united) volunteers pick science *areas*, and a central coordinator assigns projects. [BOINC Central](https://boincsynergy.ca/wiki/BOINC_Central) (Berkeley-operated, launched Nov 2021) hosts curated, widely-used science apps via BUDA "to make volunteer computing available to all scientists" — third-party apps get in **by Berkeley's curation, not self-service**.

**Verdict:** BOINC gives a mature validator/credit stack and an existing cruncher community, at the price of weeks of setup, three-platform native app maintenance, permanent LAMP-stack ops, and — for an unlisted hobby project — very uncertain volunteer acquisition.

## 2. Browser-based volunteer computing: state of the art

**Reference system.** [Wasimoff](https://github.com/wasimoff/wasimoff) (IEEE PerCom Workshops 2024, pp. 203–208; [paper](https://ieeexplore.ieee.org/document/10503392/), [Middleware '24 demo "Zero-Setup Computation Offloading to Heterogeneous Volunteer Devices Using Web Browsers"](https://dl.acm.org/doi/10.1145/3704440.3704776)) is exactly the shape Voynich@Home needs: a **Go broker** distributing **WASI WebAssembly tasks** over WebSocket/Protobuf to **browser providers** (TypeScript web workers, Vue UI; same provider code also runs under Deno for headless nodes). Volunteers join by opening a URL. MIT-licensed, Dockerized, evaluated with real devices — but the authors flag it as a research prototype **without authentication**: a working design document, not a turnkey product. Earlier academic systems ([Madoop](https://ieeexplore.ieee.org/document/8668014/) — WASM MapReduce, 64% execution-time reduction vs plain-JS; VFuse; [Pando](https://arxiv.org/pdf/1803.08426); [JSDoop](https://arxiv.org/pdf/1910.07402)) all validated the model but none became a maintained platform. The one browser-era consumer success to study is **DreamLab** (Vodafone Foundation) — a *native mobile app* that computes only while the phone charges, which is the honest answer to mobile constraints.

**Engineering facts to build on:**

- **WASM vs native:** the canonical [USENIX ATC '19 "Not So Fast" study](https://www.usenix.org/conference/atc19/presentation/jangda) measured mean slowdown of **1.55x (Chrome) / 1.45x (Firefox)**, peaks 2.1–2.5x. 2026 practice with SIMD-enabled toolchains gets tuned kernels to roughly **85–95% of native** ([WebAssembly in 2026 overview](https://www.alldevtoolshub.com/blog/webassembly-browser-tools-2026-simd-threads-wasm-3/), [Wasm runtimes in 2026](https://00f.net/2026/06/23/webassembly-runtimes-2026/)). Planning number: expect **50–80% of native throughput** per core.
- **SIMD & threads:** fixed-width 128-bit SIMD is baseline in all evergreen browsers. Threads need SharedArrayBuffer, which post-Spectre requires **cross-origin isolation** (`Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp`/`credentialless`) — trivial to set as static headers on your own domain ([web.dev threads guide](https://web.dev/articles/webassembly-threads), [SharedArrayBuffer support](https://www.testmuai.com/learning-hub/sharedarraybuffer-browser-support/)). Without isolation you fall back to one thread. Wasm 3.0 adds Relaxed SIMD/Memory64/WasmGC.
- **Background throttling:** Chrome throttles background-tab *timers* to ~1% CPU/1-per-second alignment, and after 5 minutes hidden applies [intensive throttling to once per minute](https://developer.chrome.com/blog/timer-throttling-in-chrome-88). The standard mitigation, used by every compute site: run the hot loop in a **dedicated Web Worker with no timer dependency** — workers' CPU-bound loops are not timer-throttled ([overview](https://www.getintechs.com/blog/inactive-tab-throttling)) — though OS battery-saver modes and tab freezing/discarding (especially Safari and all mobile browsers) still apply. Practical UX: "keep this tab open (pinned is fine)"; a PWA install prompt for a dedicated window; [Screen Wake Lock API](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Wake_Lock_API) (all major browsers since Jan 2025) for an opt-in foreground mobile mode — it auto-releases when the tab is hidden and can be refused on low battery.
- **WebGPU:** as of late 2025 it [ships by default in Chrome, Edge, Firefox, and Safari](https://www.webgpu.com/news/webgpu-hits-critical-mass-all-major-browsers/) (Chrome 113 in 2023; Firefox 141 Windows, Jul 2025; Safari 26, Sep 2025; Chrome Android 121), covering roughly [70% of active mobile devices by mid-2026](https://byteiota.com/webgpu-2026-70-browser-support-15x-performance-gains/). For a text/statistics workload, treat WebGPU as an optional accelerator tier, not the baseline.
- **Mobile:** browser compute is foreground-only (background tabs are frozen); realistic mobile posture is "contribute while this screen is open and charging," DreamLab-style.
- **The Coinhive shadow:** browser mining without consent ended in the [Coinhive shutdown (Mar 2019)](https://blog.avast.com/coinhive-shuts-down) after peaking at [10M+ affected users/month](https://arxiv.org/abs/2001.02975); the norm it left behind ([A First Look at Browser-Based Cryptojacking](https://arxiv.org/pdf/1803.02887)) is that in-browser compute is ethical only with **explicit opt-in before any cycle is spent, a visible meter/indicator, user-set CPU limits, and one-click stop** (Coinhive's own AuthedMine model). Some antivirus/adblock lists heuristically flag long-running WASM workers, so publish source, serve first-party JS only, and document what runs. Voynich@Home's advantage: "help decode a medieval manuscript" is a far easier consent sell than Monero.

## 3. Coordination backends a solo dev can run for ~$0

| **Supabase** (Postgres + edge functions) | [500 MB DB, 5 GB egress, 1 GB storage, 500k edge invocations, 50k MAU, 2 projects — and **projects pause after 1 week of no API traffic**](https://uibakery.io/blog/supabase-pricing) | Real Postgres + built-in auth + Realtime (nice for live dashboards). The 7-day pause is dangerous for a hobby project's quiet months; $25/mo to remove. |

**Off-the-shelf "volunteer computing over HTTP" coordinators alive in 2026:** effectively none that are production-grade. The [awesome-volunteer-computing list](https://github.com/ranjithrajv/awesome-volunteer-computing) shows Wasimoff (research prototype, no auth), Pando and distri.js (minimal/academic), AI Horde (alive and proven, but purpose-built for GPU gen-AI inference with a kudos economy), and BOINC itself. Plan to write a thin custom coordinator (~3 endpoints: lease WU, submit result, stats) and steal Wasimoff's design.

## 4. Result integrity for volunteer compute

**How BOINC does it** ([ValidationIntro](https://github.com/BOINC/boinc/wiki/ValidationIntro)): replicated computing with `min_quorum` (how many agreeing results to accept) and `target_nresults` (how many to send out); mismatches trigger extra replicas until quorum or a failure cap. **Adaptive replication** builds per-host trust so proven hosts get mostly unreplicated work (bounding expected error while cutting redundancy overhead well below 2x). **Homogeneous redundancy** exists because *native* floating point differs across CPU/compiler combinations, forcing BOINC to compare only within numerically-equivalent host classes or use fuzzy comparison. Credit (CreditNew) is granted only for validated work.

**The classical theory** ([Sarmenta, *Sabotage-tolerance mechanisms for volunteer computing systems*, FGCS 2002](https://www.sciencedirect.com/science/article/abs/pii/S0167739X01000772)): majority **voting** drives error rates down exponentially in the replication factor but costs ≥2x; **spot-checking** (known-answer "canary" jobs) reduces error linearly in work done for only a small overhead and catches persistent cheaters; **credibility-based fault tolerance** combines both to hit guaranteed error bounds at far under 2x total redundancy.

**The WASM advantage:** the WebAssembly spec makes scalar float ops **fully deterministic and bit-identical across platforms** (IEEE 754 round-to-nearest; the only nondeterminism is NaN *bit patterns*, and relaxed SIMD) — see [Nondeterminism.md](https://github.com/WebAssembly/design/blob/main/Nondeterminism.md) and the [Wasm 3.0 numerics spec](https://webassembly.github.io/spec/core/exec/numerics.html). If the kernel avoids relaxed SIMD and canonicalizes NaNs (or is integer/fixed-point), **every browser on every OS produces byte-identical output**, so validation is a hash comparison — no homogeneous redundancy, no fuzzy validators. This is a genuine structural advantage over BOINC-with-native-apps.

**Minimal honest-majority scheme for a hobby project:** (1) hash-compare **2-way replication** to different anonymous clients, escalate to a 3rd on mismatch; (2) mix in **5–10% canary WUs** with precomputed answers, indistinguishable from real work; (3) per-client reputation — after N consecutive canary+quorum passes, drop that client to ~10% random replication, BOINC-adaptive-style; (4) server-issued signed WU leases with deadlines; (5) never grant points for unvalidated work (Folding@home's passkey + bonus design exists exactly to make cheating unprofitable).

## 5. Community and dashboard precedents

What makes @home projects sticky, per [Folding@home's points/stats system](https://foldingathome.org/faq/stats): a **username + team + passkey** identity triple; points benchmarked per-WU; the **Quick Return Bonus** (extra points for fast, reliable returns — gated on the passkey, which doubles as anti-impersonation); public leaderboards; and an **open stats API** that let fans build team pages, widgets, and Discord bots ([example third-party integration](https://github.com/Phoenix-Web-Development/folding-at-home-stats)) — the ecosystem does the marketing. GIMPS has kept volunteers for 29 years on the chance of *your name on a discovery* (41M-digit prime, 2024). AI Horde's kudos system shows a modern volunteer economy working in 2026. DreamLab's "compute while charging" framing shows how to make contribution feel free. For Voynich@Home specifically, the killer dashboard is *science-forward, not points-forward*: live "hypotheses tested" counters, best-candidate-so-far tables with the contributing usernames attached — plus the Folding@home-style team leaderboard and a JSON stats API from day one.

## Recommendation

**Browser-first WASM platform on Cloudflare — "open a tab, crunch Voynich."**

- **Client:** compute kernel in Rust → WASM (deterministic: integer/canonicalized-FP, no relaxed SIMD), executed in a dedicated Web Worker pool with a visible opt-in consent card, CPU/thread slider, live progress meter, and pause button (post-Coinhive norms). Serve COOP/COEP headers to unlock cross-origin isolation. Optional WebGPU path later; optional headless Node/Deno runner for power users (same WASM binary — the "BOINC-class cruncher" tier without ever packaging native apps).
- **Coordinator:** Cloudflare Worker with ~3 endpoints (lease signed WU, submit result hash+payload, stats), D1 for WU/result/user tables, R2 for blobs (zero egress cost), static site + dashboards on Pages. Nightly GitHub Action rolls up stats and pulls validated results into the repo for the actual science.
- **Integrity:** 2-way hash-quorum + 3rd-replica escalation + 5–10% canaries + adaptive trust — cheap because WASM gives bit-exact cross-platform results.
- **Community:** accountless "instant crunch" (cookie identity), optional named accounts, teams, leaderboards, and a public JSON stats API from launch.

Judged against the criteria: **time-to-first-launch** is a few weekends of TypeScript/Rust with nothing to install or sign, versus weeks of LAMP + tri-platform packaging for BOINC; **cost** is $0 on free tiers with WUs sized so even 1,000 daily volunteers stay far under the free caps; **viral scaling** is a $5/mo flip to Workers Paid; **reach/friction** is the whole pitch — every phone and laptop that can open a link is a potential contributor, where BOINC's funnel is a client install plus a project listing Berkeley now denies to small projects; **trustworthiness** is BOINC-grade via replication+canaries, and *better* than native BOINC on determinism. The honest tradeoff — browser sessions are short and churny, so sustained FLOPs per volunteer are far below BOINC crunchers — is acceptable because Voynich statistical analysis is compute-light relative to protein folding, and the headless-runner tier recovers dedicated machines.

**Fallback:** identical browser client with the backend swapped to Supabase (mitigating the 7-day pause with a scheduled ping) or a ~$5/mo VM running a Wasimoff-style Go broker if serverless request models are outgrown. If the project ever needs serious CPU-decades, ship the kernel as a BUDA Docker app and ask to run under an existing BOINC umbrella project or BOINC Central — piggybacking is exactly what Berkeley now tells new small projects to do — rather than ever standing up a BOINC server.
